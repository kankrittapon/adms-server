## PERSONNEL

### 1. Original personnel_id mistake / root cause

`personnel_id` was never actually required by `create_human()`, `update_human()`, their Pydantic schemas, or the Add/Edit UI form (`PersonnelFormModal.tsx`) — those were already correct in 024: `personnel_id` was optional everywhere in that layer. The actual mistake was narrower and more damaging: `app/personnel_csv.py::classify_csv_rows()` used `personnel_id` as the **sole CSV matching key** and **required it on every row** (`if not personnel_id: ERROR "ไม่มีหมายเลขประจำตัว"`). Since 0 of 120 production Humans have `personnel_id` populated, this meant:
- No legacy row could ever be CSV-updated (the documented 024 limitation).
- Every single new-person CSV row — including the example row in the system's own downloadable template, whose `personnel_id` column is deliberately blank — would have been rejected as an ERROR. The template was, in effect, broken by its own import logic.

### 2. Final canonical Human identity

Unchanged and reconfirmed: `human_employees.employee_id` (UUID), generated by ADMS, stable, canonical. Never typed by an operator; never emphasized in ordinary UI (still shown only in the ADMIN technical-detail row on the Personnel detail page, per the standing internal-ID exposure rule).

### 3. Final personnel_id semantics

`personnel_id` is an **optional business field** — may be present, may be `NULL`, is never required to create, edit, or CSV-import a Human, and is never used as a matching/identity key anywhere. It is exactly as significant as `branch` or `category`: one more editable, optional attribute. Its `UNIQUE` constraint is still enforced when a value IS supplied (to prevent two different Humans accidentally sharing one), but supplying no value is always valid and never demands a backfill.

### 4. Add/edit behavior

Unchanged from 024 (already correct): `POST /api/v1/humans` requires only `display_name`; `PATCH /api/v1/humans/{id}` requires only that at least one editable field is present. Neither ever requires `personnel_id`.

### 5. CSV new-person behavior

A CSV row with no `employee_id` value is **always** classified `NEW`, regardless of whether `personnel_id` is present. The downloadable "เพิ่มกำลังพล" template (`GET /api/v1/humans/import/template.csv`) omits `employee_id` entirely and never requires `personnel_id` — its own blank-`personnel_id` example row now imports cleanly (verified by test). If an existing Human already has the exact same `display_name`, the NEW row gets a non-blocking `warning_th` advisory for human review — it is never auto-merged or auto-updated against that existing Human.

### 6. CSV round-trip update behavior

A CSV row carrying a valid `employee_id` (present only in ADMS's own export, `GET /api/v1/humans/export.csv`) is matched **exactly** against that Human and classified `UPDATE` or `UNCHANGED`. An `employee_id` that is present but does not match any existing Human becomes a friendly `ERROR` ("ไม่พบรายการกำลังพลเดิมที่ไฟล์นี้อ้างอิง กรุณาส่งออกไฟล์ใหม่จากระบบแล้วลองอีกครั้ง") — it is never silently created under that UUID and never silently dropped. `personnel_id` uniqueness is still checked and reported as a per-row `ERROR` on collision, but `personnel_id` itself plays no role in deciding NEW vs. UPDATE vs. UNCHANGED.

### 7. Name duplicate policy

Unchanged and reinforced: duplicate Thai `display_name` values across genuinely separate Humans are explicitly allowed (0 duplicates exist in production today, but the system must never reject or merge on that basis). A same-name NEW row only ever produces an advisory `warning_th`, never a block, never a silent merge, never an auto-update.

### 8. Production legacy 120-row compatibility

All 120 legacy rows (0 with `personnel_id`) are now fully compatible with the CSV round-trip flow: export them (each row carries its own `employee_id`), edit the exported file, re-import — the edit updates the correct row with zero backfill required. The Add/Edit UI form was never blocked on `personnel_id` and remains unchanged.

## ATTENDANCE

### 9. Exact 500 exception

```
NameError: name 'resolve_verified_employee_mapping' is not defined
```
Confirmed directly from the production `adms_api` container logs (`docker logs adms_api`) for the exact failing request `GET /api/v1/attendance/unattributed?limit=200`.

### 10. Exact failing function/line

`app/api/repository.py::_attribution_reasoning()`, the line calling `resolve_verified_employee_mapping(cur, pk, scan)` (used to classify why an attendance row is unattributed). The function is defined in `app/db.py` but `app/api/repository.py` never imported it — only `get_db_connection` was imported from `app.db`.

### 11. Root cause

A missing import. The bug escaped test coverage because the only prior tests covering this endpoint (`tests/test_api.py::TestAttendance::test_unattributed_paginated_with_reasoning`, `tests/test_api_auth.py`) mock `app.api.repository.unattributed_attendance` wholesale, so the real code path that calls `resolve_verified_employee_mapping()` was never actually executed by any test — a `NameError` inside it was invisible until a real request hit production.

### 12. CORS: root cause or secondary symptom

**Both** — one secondary, one genuine, both fixed:
- **Secondary**: the crash itself produced a 500 with no body other than what FastAPI's default error page/handler could produce; the browser correctly reports "no CORS header" whenever a response genuinely doesn't carry one, and prior to this fix, the *generic* exception handler's response indeed carried no CORS header — see next point.
- **Genuine, independently confirmed defect** (reproduced with a local test *before* touching the attendance bug): Starlette's `Starlette.build_middleware_stack()` special-cases any exception handler registered for the base `Exception` class — it installs that handler into `ServerErrorMiddleware`, which is the **outermost** layer, sitting *outside* `CORSMiddleware`. `app/api/errors.py::register_exception_handlers()` registers exactly such a handler (`@app.exception_handler(Exception)`) to return a safe generic `INTERNAL_ERROR` JSON envelope (no stack trace leak — that part was already correct). Because that handler's response is built and returned from outside `CORSMiddleware`, it never carried `Access-Control-Allow-Origin`, for **any** unhandled exception, not just this one. This was a real, general defect, not merely a red herring caused by the NameError.

### 13. Fix

Two independent fixes:
1. `app/api/repository.py`: added `resolve_verified_employee_mapping` to the existing `from app.db import ...` line.
2. `app/api/errors.py`: the generic `Exception` handler now computes and attaches the correct CORS headers itself (`_cors_headers_for()`), mirroring `CORSMiddleware`'s own simple-request allow-origin check against `app.state.settings.cors_origins`, before returning the JSON envelope. No wildcard CORS was added; only the exact configured allowlist is honored, and only for the `Exception`-class handler path (`ApiError`/`EnrollmentError`/`MappingError`/`RequestValidationError` handlers were already inside `ExceptionMiddleware`, which sits inside `CORSMiddleware`, so they were never affected).

### 14. 1001/1002/1003/1004 regression result

All verified via `tests/test_attendance_unattributed.py`'s fake-cursor-backed `TestUnattributedAttendanceQuery` suite (dispatches on real SQL text, not a stub of the whole function):
- **1001-style current mapped account**: scan inside its VERIFIED interval resolves (`resolver_employee_id` populated) — proves `resolve_verified_employee_mapping()` actually executes end-to-end now.
- **1002-style inactive historical device_user**: classifies `NO_MAPPING` safely, no crash.
- **1004-style removed account** (no `device_users` row left for the pk): classifies `NO_DEVICE_USER` safely, no crash.
- **1003-style reused terminal ID / new incarnation**: two VERIFIED intervals on the same `device_user_pk` — an old scan resolves only against the old interval's employee, a new scan resolves only against the new interval's employee; neither leaks into the other.
- **Closed historical mapping** (`valid_to` set): a scan before `valid_to` still resolves correctly — closing a mapping never retroactively hides the identity valid at scan time.

### 15. Live endpoint result

Verified against production after deployment (§21) — `GET /api/v1/attendance/unattributed?limit=200` returns `200 OK` (previously `500`); confirmed via container logs showing no further tracebacks and a live authenticated request from the deployed console.
